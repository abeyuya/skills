# PR レビュー時の技術観点チェックリスト参考ガイド

以下はレビューで **何を見るか (技術観点)** に関する参考ガイドです。anthropics/claude-code リポジトリの [`pr-review-toolkit`](https://github.com/anthropics/claude-code/blob/5bf19945e4e9e38d298ddc2befd5c30a7d504fb8/plugins/pr-review-toolkit/README.md) が提供する 6 種類のレビュー専門エージェントの観点を、本リポジトリのレビュー手順から呼び出せる形に整理したものです。

レビューコメントの **書き方・体裁** (重要度ラベル / ノイズ抑制 / 粒度 など) は本ファイルの対象外で、`/pr-review-style-reference` 側で別途指定する想定です。

レビュー方針は caller プロジェクト (ユーザー) に委ねる前提で、以下のいずれの使い方でも構いません。

- そのまま採用する
- 採用した上で caller 側のカスタム指示を上に重ねる
- 採用せず無視する

caller 側のカスタム指示と本ガイドラインの内容が矛盾する場合は caller 側を優先してください。

## 引数 (`$ARGUMENTS`)

レビューで重点的に見る観点を切り替える。

- 引数なし (デフォルト): `focus=all` と同じ扱い。下記 6 観点すべてを確認対象にする。
- `focus=all`: 6 観点すべてを確認対象にする (明示指定用)。
- `focus=tests`: 「テスト網羅性」観点のみに絞る。
- `focus=errors`: 「エラーハンドリング / silent failure」観点のみに絞る。
- `focus=comments`: 「コメント / ドキュメント」観点のみに絞る。
- `focus=types`: 「型設計」観点のみに絞る。
- `focus=quality`: 「一般的なコード品質 (CLAUDE.md 準拠 / バグ / スタイル)」観点のみに絞る。
- `focus=simplify`: 「コード簡潔性 / 可読性」観点のみに絞る。

複数指定したい場合はカンマ区切り (例: `focus=tests,errors`) を許容する。指定された観点以外は本レビューでは触れない。

## 基本方針

- 変更された行 (diff の中身) を中心に見る。リポジトリ全体の棚卸しはしない。
- 観点ごとに「該当なし」も明示してよい。無理に指摘を捻り出さない。
- 各観点で見つかった問題は、`/pr-review-style-reference` の重要度ラベル (`[must]` / `[should]` / `[nit]` / `[q]`) と粒度ガイドに沿ってインライン or 総括に振り分ける。

## 観点 1: テスト網羅性 (pr-test-analyzer 相当)

**目的:** 行カバレッジではなく振る舞いベースで、変更が壊れたら検知できるかを確認する。

確認項目:

- 追加・変更された関数/メソッドの **主要な振る舞い** がテストで担保されているか。
- 境界値・エッジケース (空入力、null/undefined、上限値、片方だけ条件成立、等) が押さえられているか。
- 異常系 (例外パス、エラー戻り値、タイムアウト、リトライ) がテストされているか。
- テストが「実装と一緒に同じバグを再現するだけ」になっていないか (実装をミラーしただけのテストは指摘対象)。
- 重要な分岐・契約 (公開 API / DB スキーマ / 外部 I/F) のうちテスト未到達のクリティカルギャップがないか。

## 観点 2: エラーハンドリング / silent failure (silent-failure-hunter 相当)

**目的:** 例外や失敗を握り潰していないか、失敗が観測可能かを確認する。

確認項目:

- `catch` / `except` / `rescue` ブロックで **何もしていない** 箇所がないか (ログも再 throw もなし)。
- 失敗時に「それっぽいデフォルト値」を返してしまい、呼び出し側が成功と誤認する設計になっていないか。
- ログを出している場合、後から原因究明できる情報量か (例外オブジェクト / 入力サマリ / 相関 ID 等)。
- リトライやフォールバックが「本来エラーにすべきケース」まで覆い隠していないか。
- 外部 I/O (HTTP / DB / FS / queue) のタイムアウト・部分失敗の扱いが妥当か。

## 観点 3: コメント / ドキュメント (comment-analyzer 相当)

**目的:** コメントが嘘をついていないか、保守の足を引っ張らないかを確認する。

確認項目:

- コメントの記述と実コードの挙動がずれていないか (リネーム/挙動変更の取りこぼし)。
- 「なぜそう書いたか」を説明する価値のあるコメントが、機械的な「何をしているか」の繰り返しになっていないか。
- 公開 API / 公開型 / 公開関数のドキュメントが、引数・戻り値・例外/失敗条件・副作用を必要十分に説明できているか。
- TODO / FIXME / HACK が放置されていないか。残すなら追跡できる形 (Issue 番号や所有者) になっているか。
- 古くなったコメント・誤解を招くコメントがないか。

## 観点 4: 型設計 (type-design-analyzer 相当)

**目的:** 新規・変更された型が不変条件を表現できているかを確認する。

確認項目:

- 不正な状態を **そもそも作れない** ように型でガードできているか (例: 直和型・Branded type・Non-empty 系・必須プロパティ)。
- 1 つの型が責務過剰 (フィールドの組み合わせで意味が変わる、optional の依存関係が暗黙) になっていないか。
- 「文字列 1 本」「数値 1 本」になっていて、ドメインの区別 (UserId / OrderId / 通貨 / 単位) が消えていないか。
- 不変条件をコンストラクタ / スマートコンストラクタ / バリデータ等で実際に強制しているか (ドキュメントに頼っていないか)。
- 公開型の互換性破壊が無自覚に入っていないか。

## 観点 5: 一般的なコード品質 (code-reviewer 相当)

**目的:** プロジェクト規約・基本的な品質・潜在バグを確認する。

確認項目:

- リポジトリの `CLAUDE.md` / コーディング規約 / 既存パターン に沿っているか。
- 明らかなバグ (off-by-one, 非同期の取りこぼし, 競合, リソースリーク, 認可抜け, インジェクション系) がないか。
- 命名・配置・粒度がプロジェクト内の既存コードと整合しているか。
- 不要なデバッグ出力 / コメントアウトされた死んだコード / `console.log` 等の残骸がないか。
- 機密情報 (秘密鍵・トークン・本番接続情報) を誤ってコミットしていないか。

## 観点 6: コード簡潔性 / 可読性 (code-simplifier 相当)

**目的:** 動くだけでなく、後から読む人が理解しやすいかを確認する。

確認項目:

- 不要なネスト / 早期 return で潰せる入れ子がないか。
- 重複した分岐・抽出可能な共通処理を、過剰でない範囲でまとめられないか (逆に、無理な抽象化を作っていないか)。
- 「賢すぎる」一行・密度の高すぎる三項演算 / チェーンになっていないか。
- フラグ引数や巨大関数で責務が混ざっていないか。
- 既存ユーティリティ・既存パターンで置き換えられる「車輪の再発明」になっていないか。

ただし「簡潔化指摘」は強制ではない。**機能を壊さずに読みやすくなる場合に限り** 提案し、好みレベルにとどまるものは `[nit]` 以下に抑える。

## 出力時の注意

- 上記 6 観点はあくまで **チェックリスト** であり、観点ごとに必ずコメントを 1 件出すノルマではない。
- 同一の根本原因が複数観点に跨がる場合は、最も妥当な 1 観点に寄せて 1 箇所だけ指摘する (観点ごとの再掲はしない)。
- 各指摘の文体・重要度ラベル・件数制御は `/pr-review-style-reference` の指定に従う。

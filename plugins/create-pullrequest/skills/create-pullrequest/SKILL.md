# Create Pull Request Skill

コミット済みブランチに対する GitHub Pull Request 作成を 1 つの skill 呼び出しで完結させる。未 push の場合は push 承認後に PR 作成へ進む。PR タイトル形式・本文テンプレート・Draft 既定・CODEOWNERS 委譲・ラベル運用といった PR 作成時の判断をまとめて適用する。

本 skill は **PR を作る** ところだけを担当する。新たな commit の作成や、PR 作成後のレビュー投稿には踏み込まない（未 push ブランチに対する push 承認は本 skill 内で扱う）。

## 入力 (任意)

すべて省略可。省略時は本文の手順で自動取得・推測する。

- `BASE_BRANCH`: PR のマージ先ブランチ。省略時は `main`。
- `READY`: `true` を渡すと Draft ではなく Ready の PR として作る。省略時は Draft。

## 手順

### Step 1. 前提確認

- `git status --porcelain` でワーキングツリーを確認する。
  - tracked-modified (`M` / `A` / `D` / `R`) が残っていれば、先に commit を作るよう案内して停止する。
  - untracked (`??`) のみの場合は警告を 1 行出して続行する（ローカル一時ファイルの可能性があるため停止しない）。
- `git rev-parse --abbrev-ref HEAD` で現在ブランチ名を取得する。`main` / `master` / default branch 自身の場合は、先に作業ブランチを切るよう案内して停止する。
- ブランチ名が `feat/` / `fix/` / `feature/` / `chore/` / `docs/` / `codex/` のいずれかから始まることを推奨する。外れていればその旨を 1 度だけ警告して続行する（ユーザーが意図して別命名にしている可能性があるため停止はしない）。

### Step 2. リポジトリ識別情報の取得

- `gh repo view --json nameWithOwner -q .nameWithOwner` で `OWNER/REPO` を取得する。
- 取得失敗時は `gh auth status` を案内して停止する。
- `BASE_BRANCH` が未指定なら `main` を採用する。

### Step 3. push 状態の確認

- `git rev-parse --abbrev-ref --symbolic-full-name @{u}` で upstream の有無を確認する。
- upstream が無い場合: `git push -u origin <branch>` を提案し、ユーザー承認を得てから実行する。
- upstream はあるがローカルが先行している場合 (`git status -sb` の `[ahead N]`): `git push` を提案し、ユーザー承認を得てから実行する。
- リモートが先行している (`[behind]`) 場合は、`git pull --rebase` 等を促して停止する (skill 側で自動 rebase はしない)。ユーザーが rebase 完了後にこの skill を呼び直す前提で案内する。
- push 承認をユーザーに求める際は、「push 自体は不可逆ではなく、Step 8 で PR タイトル / 本文を改めて承認します」と一言添えて、内容確認が後段にあることを明示する。

### Step 4. 既存 PR の重複チェック

- `gh pr list --head <branch> --base <BASE_BRANCH> --state open --json number,url --limit 1` を実行する。
- 既に open な PR があれば、その URL を案内して停止する (重複作成防止)。
- closed/merged の PR が同 head/base に存在する場合は、その URL を 1 行案内した上で新規作成に進む（サイレントには進めない。意図せず古い PR を上書き再生したと誤解されないように告知する）。

### Step 5. コミット履歴と差分の取得

- `git log <BASE_BRANCH>..HEAD --pretty=format:'%h %s%n%b' --no-merges` でコミット履歴を取得する。
- `git diff --stat <BASE_BRANCH>...HEAD` で変更ファイル一覧と概況を取得する。必要に応じて `git diff <BASE_BRANCH>...HEAD` で本文も読む。
- 関連 Issue 候補の抽出:
  - **ソース**: `git log` で取得したコミット件名 / 本文（差分テキストは対象外）。
  - **形式**: `#<数字>` の正規表現 (`#\d+`)。
  - **除外**: revert コミットの本文（`This reverts commit ...` を含む段落）、`Co-Authored-By:` 行、URL 内の `#fragment` は除外する。
  - **注意**: `#\d+` は Issue 番号と PR 番号を区別できない。抽出結果は「関連 Issue 候補」であって確定値ではないため、Step 7 でユーザーに採否を確認する。
  - 抽出結果は重複排除した昇順リストにする。

### Step 6. PR タイトルの生成

- `<scope> <type>: <何を><なぜ>変更したか` の 1 行で組み立てる。
- **type 一覧（7 種）**: `feat`（機能追加） / `fix`（バグ修正） / `refactor`（挙動を変えない内部改善） / `style`（UI / スタイル調整） / `docs`（ドキュメント） / `test`（テスト） / `chore`（その他雑務）。
- **scope の決め方**: 英語小文字、grep しやすい名前。ファイルパス・パッケージ名・モノレポのアプリ名から導出（例: `auth` / `admin` / `api` / `db` / `ui` / `config` / `deps` / `infra` 等）。
- 単一コミットの場合は、そのコミット件名をそのまま採用候補にする。
- 複数コミットの場合は scope/type を共通項から推測し、候補をユーザーに提示する。
  - scope が真に独立した複数領域に分かれている場合（例: `auth` / `db` / `ui` のように共通項が取りづらい）は、PR タイトル候補 2〜3 件に加えて **「PR を分割する」「commit を squash して 1 つの scope に集約する」** という選択肢もユーザー判断として併記する。
- **「なぜ」が差分・コミット本文・周辺コード・会話履歴から読み取れない場合、または推測の確信度が低い場合は、それっぽい理由を捏造せず必ずユーザーに 1 度尋ねる**。「薄い推測より正確な沈黙」を優先する。
  - 複数コミットで複数の「なぜ」が不明な場合は、**1 メッセージにまとめて全項目をヒアリング**する（ユーザー往復回数 < 確認対象数 を維持）。
- scope / type が複数候補で割れて確信度が低い場合も同様にユーザーに候補 (2〜3 件) を提示して選んでもらう。

### Step 7. PR 本文の組み立て

**処理パイプライン**（この順で実行する）:

1. リポジトリ root の `.github/pull_request_template.md` を `Read` ツールで読み込む。存在しなければ、そのリポジトリで通常使う PR 本文構成が不明であることをユーザーに伝えて確認する。
2. テンプレートが存在する場合は、セクション構成と見出しを可能な限り維持する。テンプレートが存在しない場合は、以下の 5 セクションを標準構成として使う。
3. 各セクションの中身を後述のルールで埋める。
4. テンプレ内の `<!-- ... -->` ヒントコメントを **全て** 最終本文から除去する（人間に提示する完成本文には不要）。
5. ポリシー検査（後述の最終確認）を行ってから Step 8 へ進む。

**標準セクション**:

- `# 関連Issue & リンク`
- `## 変更内容`
- `## 動作確認スクリーンショット`
- `## レビュー観点 / 補足`
- `## レビュー依頼前のチェックリスト`

**各セクションの中身を埋めるルール**:

- `# 関連Issue & リンク`
  - Step 5 で抽出した `#<数字>` を `- #N` 形式で列挙する。
  - 抽出ゼロなら `なし` の 1 行に置き換える。
  - 抽出した Issue 番号が PR と本当に関連するか確信度が低い場合 (例: 過去コミットから引き継がれているだけの可能性) は、列挙候補をユーザーに見せて採否を確認する。

- `## 変更内容`
  - コミット履歴と差分から「何を」「なぜ」を箇条書きで再構成する。粒度はコミット単位を基本とし、関連の薄い差分は別項目に分ける。
  - 各項目について、コミットメッセージや差分から確信度高く抽出できないものがあれば、当該項目をユーザーに提示して内容を確認する (捏造禁止)。

- `## 動作確認スクリーンショット`
  - ユーザーから添付の指示があれば貼る。
  - 指示が無く UI 変更も無い場合は実行ログ等の有無を尋ね、何も無ければ `なし` と記す。
  - dry-run / 非対話セッションで「尋ねる」相手がいない場合は、`なし` をデフォルトとして採用する。

- `## レビュー観点 / 補足`
  - 主要な設計判断・レビュー時に注意してほしい点・未対応の残課題があれば 1〜3 行で書く。
  - これらが読み取れない場合は、ユーザーに「特になければ『なし』にしますが、何か明記したいですか？」と一度尋ねた上で決める。
  - 確信度が低くかつ書く材料が無い場合は `なし` を採用してよい（「尋ねた結果『なし』」と「材料無しで『なし』」は最終本文上同一）。

- `## レビュー依頼前のチェックリスト`
  - AI が PR 本文を作成する場合、テンプレート内のチェックリストは原則 `[ ]` のまま残す。人間が確認してからチェックする運用を優先する。

**最終確認（ポリシー検査）**:

- 組み立てた本文・タイトルに、他リポジトリ名 / 外部プロジェクト名 / 他社プロダクト名が含まれていないことを確認する（対象リポジトリ内の skill 名・パッケージ名・コード固有語は除く）。
- `<!-- ... -->` 形式の HTML コメントが最終本文に残っていないことを確認する。

### Step 8. ユーザー承認

- skill 呼び出し時に `READY=true` の指定があるかをここで確認する。指定がなければ Draft 既定で作成する（呼び出し時の入力に無い限り会話履歴からの推測で Ready 化しない）。
- Step 6 / Step 7 で発生した部分質問（「なぜ」のヒアリング・関連 Issue 採否確認・レビュー観点の有無等）への回答を全て受け取り終わってから、組み立てた PR タイトルと本文を 1 ブロックでユーザーに提示し、最終承認を取る。
- 部分質問と最終承認は二段階に分ける。**「最終承認だけで部分質問にも回答済み」と解釈してはいけない**。
- 修正要求が出たら反映してから再提示する。**ユーザーの承認を得るまで `gh pr create` は呼ばない**。

### Step 9. Draft で PR を作成

- 本文は `Write` ツールで一時ファイルに書き出し、`gh pr create` には `--body-file` で渡す。HEREDOC 渡しはエスケープ事故の温床なので使わない。
- 一時ファイルの命名規約: `mktemp -t pr-body` で生成するか、明示的に `/tmp/pr-body-$(date +%s)-$$.md` 形式を採用する（並列実行時の衝突回避が目的）。
- 実行コマンド（`<OWNER>` / `<REPO>` / `<BASE_BRANCH>` / `<branch>` / `<title>` / `<tmpfile>` は **必ず実値に置換** してから実行する。プレースホルダのまま走らせない）:

  ```sh
  gh pr create \
    --repo <OWNER>/<REPO> \
    --base <BASE_BRANCH> \
    --head <branch> \
    --title "<title>" \
    --body-file <tmpfile> \
    --draft
  ```

- `READY=true` が明示されている場合のみ `--draft` を外す。デフォルトは Draft で作成する。
- レビュアー (`--reviewer`) / ラベル (`--label`) / マイルストーン / プロジェクトは **指定しない**。CODEOWNERS による自動アサインに任せる。
- コマンド実行直前に、`--no-verify` などフックスキップ系オプションが含まれていないことを確認する。
- 失敗した場合は再試行せず、`gh` の出力をそのままユーザーに見せて停止する。

### Step 10. 作成後の案内

- 取得した PR URL・PR 番号・採用した PR タイトル・関連 Issue を 1 ブロックでまとめて報告する。
- ブラウザで開きたい場合は `gh pr view --web <PR_NUMBER>` を実行するよう案内する (skill から自動でブラウザを開かない)。
- AI レビューを走らせるラベル等の運用がある場合は、必要なコマンドを案内するだけに留める (skill 側で自動付与はしない)。

## 守ること

- `--no-verify` などフック / 検証スキップ系オプションは使わない。
- `gh pr create` を `--draft` 抜きで呼ぶのは `READY=true` が明示された場合だけ。デフォルトは Draft。
- PR 本文の「レビュー依頼前のチェックリスト」は AI 側で原則チェックしない。
- レビュアー / ラベル / マイルストーン / プロジェクトは指定しない。CODEOWNERS と人間の判断に委ねる。
- `gh pr create` が失敗した場合は再試行しない。エラーをそのままユーザーに見せて停止する。
- 本 skill は新たな commit の作成や PR 作成後のレビューには踏み込まない。
- **確信度の低い箇所は捏造せずユーザーに尋ねる**: PR タイトルの「なぜ」が読み取れない場合・scope/type が割れる場合・本文セクションの趣旨が推測の域を出ない場合は、薄い推測で埋めずに必ずユーザーに 1 度確認する。「正確な沈黙」は「それっぽい捏造」より保守性に貢献する。
- **他リポジトリ名・外部プロジェクト名を含めない**: PR タイトル / 本文 / コミットメッセージには、対象リポジトリ外の固有名詞を一切書かない。このリポジトリ単体の文脈で記述する。
